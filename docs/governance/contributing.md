# 研究协作

## 从讨论到基线

理论探索继续在主 Chat。形成可检验任务时，由接手的 Agent 从仓库读当前基线、整理假设和验收口径、做实验，并把可共享结果写回同一仓库。人或后续 Agent 可以按假设、实验编号和提交版本接续；拥有仓库读取权限的 Chat 可以直接读取记录。授权按实际会话与仓库连接处理。

研究问题、反例或来源补充可用一条 Issue 或评审意见。一个实验的改动应给出假设编号、版本、对照、结果与适用范围，保留失败与分叉。稳定结论更新对应的主张和当前状态；研究定位或阶段发生实质变化时再调整 README。决策改变更新[决策记录](decision-log.md)，时间线写入[版本记录](../../CHANGELOG.md)。

## 每次聊完如何写回

项目发起人在主 Chat 说：

> 把这一阶段归档，按 Tako 流程准备发布。

这沿用“把这一阶段归档并更新仓库”的授权范围，整理该阶段可共享的研究内容。此次已经走通的路径是 **Chat 准备内容与文件，项目发起人转交，Tako 在有写权限的本机发布，Chat 核对远端**。Chat 直接调用 Tako 的接口尚未验证；当前仍需一次人工转交。

| 环节 | 执行方 | 交付与完成依据 |
| --- | --- | --- |
| 确定基准 | Chat | 读取远端 `main`，记录完整基准 commit，再建立本轮候选修改。 |
| 整理与检查 | Chat | 更新受影响文档和资产，检查相关内容，保存本地候选 commit；首页保持稳定的研究叙事。 |
| 准备发布包 | Chat | 输出增量 ZIP、实际文件清单和一段已填好的 Tako 接手指令。 |
| 转交 | 项目发起人 | 将同一条交付回复与附件交给 Tako，无需重述研究过程。 |
| 合并与发布 | Tako | 核验包和当前远端，按基准比较合并，执行相关检查，再提交、推送。 |
| 回执与验收 | Tako、Chat | Tako 返回提交链接和检查结果；项目发起人贴回链接或告知“已推送”，Chat 读取远端，核对本轮内容。 |

本地文件完成、本地 commit 完成、远端 push 完成、远端内容已核验，分别报告。遇到明确的凭据或写权限缺口，直接保留候选内容与交接包，不重复尝试同一失败入口，也不把权限元数据当作实际写入成功。当前流程复用 Tako 已有的发布能力。

### 发布包的固定内容

ZIP 只包含需要新增或覆盖的文件，内部路径直接对应仓库相对路径，不额外套根文件夹。清单单独附在同一交付回复中；没有出现在 ZIP 中的仓库文件应保留。

清单由同一次 Git 差异和实际打包字节生成，至少包含：

- 目标仓库、分支、基准 commit、本地候选 commit、候选完整 Git tree。
- ZIP 名称、大小和 SHA-256；每个文件的操作类型、相对路径、大小和 SHA-256。
- 删除路径及改名前后路径；没有则明确写“无”。不能根据 ZIP 缺少某个文件推断删除。
- 已完成的相关检查、已知缺口、研究暂停或恢复状态，以及此次获授权的修改范围。

Tako 可以从同一 ZIP 和清单继续发布。包的文件数按每轮实际差异生成，46 个只属于首次归档包。

### Tako 如何处理基准变化

先读取本机仓库指令，核对工作区已有修改，再获取远端最新状态。发布前再次确认远端版本。

- **远端等于基准：** 应用增量后，暂存内容对应的完整 Git tree 应与清单一致。
- **远端已经前进：** 比较基准、当前远端和本轮候选，保留远端已有工作，合并本轮修改。此时完整 Git tree 可能与清单不同，需要说明差异。
- **发现语义冲突：** 可以明确判断的格式、链接和去标识修正直接合并并记录；涉及研究结论、证据级别或任务优先级的冲突，回到主 Chat 复核。

不覆盖无关工作，不强推。Tako 重新提交后的 commit SHA 可以与 Chat 候选不同；验收依据是实际内容、差异和 Git tree。

### 每次附给 Tako 的接手指令

以下内容由 Chat 填入该轮真实文件名与基准后随包提供：

> 按附带发布包和清单更新 `JoeSangAI/brandtopia` 的 `main`。先核验 ZIP 与逐文件校验值，再比较清单基准和当前远端，保留已有改动并处理新增、修改、删除与改名。完成相关检查后提交推送，返回 commit URL、实际修改范围、合并说明及远端核验结果。研究状态以仓库当前记录为准；此次只执行交接清单中的工作。

### 最小发布回执

一段文本即可，无需新增状态系统：

```text
目标：JoeSangAI/brandtopia / main
发布 commit：<完整 SHA 与 URL>
发布 tree：<实际 Git tree>
实际变更：<新增 / 修改 / 删除 / 改名数量>
基准变化与合并：<无，或具体处理>
核验：<执行了什么检查，结果如何>
远端内容：<已核对，或未核对的具体原因>
```

Chat 读取远端回执对应版本及当前 `main`，确认本轮内容仍在，并保留同时发生的后续修改。回执和核验结果保留在本轮交付记录；无需为了登记“已发布”再产生一轮提交。

## 评审顺序

1. 看研究判断。比较组是否隔离了待测机制，结果能否推翻原假设。
2. 看实现与资产。按记录复跑，检查事件、参数与日志能否追到同一版本。
3. 看证据与权限。核对级别、来源及[资料边界](privacy.md)，把私密原文留在授权来源。

实证资产只保留有权限共享且为复核所必需的部分。复用已有日志、编号和文档入口。
